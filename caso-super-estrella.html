Super La Estrella: sales, payments and inventory

The backend for a supermarket chain: a SQL Server 2022 database where the business rules live, a Node.js REST API as the only way in, and a React dashboard with a live demo. A two-person project for Databases 1.

Open the live demo View the code
My part
Database (DDL, data load, triggers) and the sales and payments flow
Team
2 people · Databases 1, USAC
Data
19 tables, 22 foreign keys, 9,084 rows loaded
Stack
SQL Server 2022, T-SQL, Node.js, Express, React, Vite, Docker

The problem

A sale touches several tables at once: it has to check the product's stock at the store where it's sold, subtract it, record the payments and mark the sale as paid once the total is covered. If that logic is spread through application code, any client writing straight to the database can leave the inventory inconsistent.

The rules live in the engine

Decisiones de diseño

  1. Triggers para lo que no se puede romper. Insert_Detalle valida y descuenta el stock de la tienda de la venta; si no alcanza, lanza el error 50001 y se revierte la transacción completa. Insert_Pago marca la venta como PAGADA cuando los pagos llegan al total.
  2. Pagos inmutables. Dos triggers INSTEAD OF bloquean borrar o modificar un pago, y Delete_Detalle devuelve el stock a la tienda si se quita un detalle.
  3. El API es la única puerta. Node.js no repite la lógica de los triggers ni hace JOINs para los reportes: traduce HTTP a SQL parametrizado. El login del API no puede cambiar la estructura y el de DBeaver es de solo lectura.
  4. Una base que se arma sola. Un contenedor db-init ejecuta los scripts por prefijo: el DDL solo si no hay tablas, la carga con BULK INSERT solo si están vacías, y triggers, vistas y usuarios siempre, porque son idempotentes.

Resultados

  • 19 tablascon 19 llaves primarias, 22 foráneas, 5 CHECK y 2 UNIQUE
  • 5 triggersy 3 vistas analíticas para los reportes
  • 9 084 filascargadas desde 19 archivos CSV al levantar el contenedor

Pruébalo

En el demo en vivo el API y los triggers se simulan en el navegador con el mismo dataset: registra una venta en «Nueva venta» y pide más de lo que hay en stock para ver el error del trigger. Para correrlo con SQL Server real:

git clone https://github.com/akamariano/super-estrella-bd1
cd super-estrella-bd1
cp .env.example .env
docker compose up -d
cd backend && npm install && npm run dev

Design decisions

  1. Triggers for what can't break. Insert_Detalle checks and subtracts stock at the sale's store; if there isn't enough, it throws error 50001 and the whole transaction rolls back. Insert_Pago marks the sale as PAGADA once payments reach the total.
  2. Immutable payments. Two INSTEAD OF triggers block deleting or changing a payment, and Delete_Detalle returns stock to the store when a line item is removed.
  3. The API is the only door. Node.js doesn't repeat the trigger logic or do JOINs for reports: it translates HTTP into parameterized SQL. The API's login can't change the schema and DBeaver's is read-only.
  4. A database that sets itself up. A db-init container runs scripts by prefix: the DDL only if there are no tables, the BULK INSERT load only if they're empty, and triggers, views and users every time, since they're idempotent.

Results

  • 19 tableswith 19 primary keys, 22 foreign keys, 5 CHECK and 2 UNIQUE constraints
  • 5 triggersand 3 analytical views for reporting
  • 9,084 rowsloaded from 19 CSV files when the container starts
